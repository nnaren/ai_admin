## Intent (why the user wants this)

The user runs multiple self-hosted AI gateway processes (proxies / routing layers in front of upstream model APIs) on their dev box. Today they juggle terminals, manual `kill` / restart, and ad-hoc health checks. They want a **single local control surface** that shows what's running, lets them start/stop each gateway, and surfaces health. They value being able to **edit the YAML config by hand**, with the panel being an overlay on top of that file rather than a replacement. They anticipate extending the panel to a second domain (likely model-API usage / code-plan packages) and want a generic extension point from day one so they don't have to rewrite the core.

## Desired Outcome

A single-operator, local-first web dashboard that:

1. Renders one card per configured gateway, each showing running/stopped, PID, listen port, health URL, and last health probe result.
2. Lets the operator start / stop each gateway via per-gateway user-defined shell commands stored in the YAML.
3. Reads and writes the YAML config; external edits to the YAML are picked up by the panel without restart.
4. Exposes a **generic, route-registered tab host** so additional tabs (e.g. model-API usage) can be added without changes to the tab host itself.

## In-Scope (MVP)

### F1. Gateway list & status rendering
- Each entry in `config/gateways.yaml` becomes one card on the default tab.
- Each card shows: name, running/stopped badge, PID (if running), listen port, health URL, last health check status (timestamp + ok/fail + HTTP code or error).
- Polling cadence is configurable; **default 3 s**, easy to override.

### F2. Start / stop
- Each gateway has `startCommand` and `stopCommand` strings in YAML.
- Clicking "Start" on a stopped card runs `startCommand` as a child process via the backend.
- Clicking "Stop" on a running card runs `stopCommand`; the backend tracks PID and waits (bounded) for exit, falling back to SIGTERM then SIGKILL if needed.
- The panel never invents process-management semantics beyond "run this command, capture PID if you can, terminate on stop."

### F3. YAML source-of-truth
- The canonical config is `config/gateways.yaml` on disk.
- All reads in the panel go through the backend, which is the only writer.
- Edits made through the panel UI (add / rename / delete gateway, edit fields, edit commands) round-trip through the YAML, preserving formatting and comments where reasonable.
- Backend watches the YAML file; external edits trigger a debounced reload (proposed 250 ms) and the UI re-derives state from the file.

### F4. Health probing
- Each gateway may declare `healthUrl` (optional). When present, the backend probes it with HTTP GET (default timeout 2 s) on the polling cadence.
- Last probe result is exposed to the UI as `{ ok: boolean, httpCode?: number, error?: string, at: ISO8601 }`.

### F5. Generic tab system
- Frontend ships a tab host that renders tabs from a route-registered registry.
- MVP ships exactly one tab (`gateways`).
- Adding a new tab requires: a React component module + a registry entry; **no change to the tab host**. The registry entry is plain TypeScript code in the frontend bundle (no remote plugin loading, no `eval`, no runtime fetch-and-mount).
- Tab host must NOT bake in any business/API assumptions (e.g. it must not import the gateways YAML schema).

### F6. Local server lifecycle
- Backend defaults to `127.0.0.1:8787`.
- A separate top-level `server.yaml` (or equivalent) exposes:
  - `bind`: `127.0.0.1` (default) | `0.0.0.0`
  - `port`: integer (default `8787`)
- LAN mode is opt-in by editing the server config. No auth is added in MVP.

### F7. Backend ↔ Frontend contract
- REST/JSON over HTTP from the SPA to the Fastify backend.
- Endpoint surface (minimum, illustrative):
  - `GET /api/gateways` — list with live status merged in.
  - `POST /api/gateways/:id/start` — start a gateway.
  - `POST /api/gateways/:id/stop` — stop a gateway.
  - `PUT /api/gateways/:id` — edit a gateway entry (writes back to YAML).
  - `POST /api/gateways` — add a gateway entry.
  - `DELETE /api/gateways/:id` — remove a gateway entry.
  - `GET /api/health` — backend liveness.
  - `GET /api/tabs` — list registered tabs (returns `[{id, path}]`).
- Exact endpoint names and payload shapes are OMX-decidable, as long as the semantics above hold.

## Out-of-Scope / Non-Goals

Per Round 7, **no formal exclusion list**. Scope is defined by inclusion. The following are explicitly **deferred / future**, NOT excluded (they may be added later):

- Multi-node / remote gateway control
- Log streaming / tailing
- Auto-restart on crash
- Docker / systemd abstraction
- Mobile-responsive UI

If any of the above becomes in-scope later, the generic tab system + YAML authority model are expected to absorb it without re-architecture.

## Constraints

- **Stack:** Vite + React + TypeScript (frontend), Fastify + Node.js (backend), YAML (config). Single localhost backend.
- **Networking:** Backend binds `127.0.0.1:8787` by default; `bind` and `port` are user-editable in `server.yaml`.
- **Authority:** YAML is the single source of truth. The backend is the only writer; the UI is a thin client.
- **Process control:** Commands are user-defined strings. The backend executes them; it does not parse, template, or interpret them beyond capturing exit and (when feasible) PID.
- **Extensibility:** Tab system must remain generic and decoupled from any specific business / API shape.

## Testable Acceptance Criteria

The MVP is considered complete when **all** of the following hold:

### A. Configuration & authority
- A1. A YAML file at `config/gateways.yaml` with N (≥ 0) gateway entries is the single source of truth.
- A2. Editing the YAML externally (text editor) and saving causes the panel UI to reflect the change within ≤ 1 s, without restart.
- A3. Editing the YAML externally to add a new gateway makes its card appear on the panel without restart.

### B. Card rendering
- B1. Each card displays: name, running/stopped, PID (when running), port, health URL, last health status.
- B2. Polling cadence is configurable; with default settings, status updates visible within ≤ 5 s of state change.

### C. Start / stop
- C1. Clicking "Start" on a stopped gateway runs the gateway's `startCommand`. On success, the card transitions to running with a non-empty PID within ≤ 3 s.
- C2. Clicking "Stop" on a running gateway runs `stopCommand`. The card transitions to stopped within ≤ 5 s; PID field clears.
- C3. If `startCommand` exits non-zero, the card surfaces the error and remains in stopped state.
- D. Editing gateways via the UI (add, rename, delete, edit fields, edit commands) writes back to the YAML and survives a panel reload.

### E. Generic tabs
- E1. The frontend tab host renders tabs from a registry; deleting or stubbing the `gateways` tab leaves the host functional.
- E2. Adding a new tab requires only (a) a React component module and (b) a registry entry. No changes to the tab host code.
- E3. The tab host does not import the gateways YAML schema.

### F. Local server lifecycle
- F1. With default config, backend listens on `127.0.0.1:8787`.
- F2. Setting `bind: 0.0.0.0` in `server.yaml` causes the backend to listen on all interfaces (verified with `lsof` / `ss`).
- F3. No auth middleware is added in MVP; this is an explicit choice, documented in README.

### G. Health probe
- G1. A gateway with `healthUrl` shows `ok: true` and the HTTP code after a successful probe.
- G2. A gateway with an unreachable `healthUrl` shows `ok: false` and an error string after the timeout (default 2 s).

### H. End-to-end smoke
- H1. From a clean clone: `pnpm install && pnpm dev` (or chosen equivalent) brings up the panel reachable at the configured address, with a sample YAML showing at least 2 example gateways.

## Scenario / Edge-Case Pressure Findings

These scenarios were not asked directly in the interview but were synthesized from the locked decisions to verify scope robustness. They should drive test coverage:

1. **YAML edited while a gateway is running.** Backend must not stop the process; it must update the in-memory projection and re-render the card. If the running entry was renamed or removed, the supervisor keeps the old PID until explicitly stopped (no surprise kills from external edits).
2. **Two UIs / two browsers.** Polling + file-watch must remain consistent across multiple connected clients. No race condition should let one client's edit clobber another's in-flight start/stop.
3. **`startCommand` exits 0 but the process immediately dies.** Card should re-poll and reflect stopped state. The panel must not "stick" on running.
4. **`stopCommand` is missing or empty.** Backend should fall back to SIGTERM by PID, then SIGKILL after a bounded timeout.
5. **YAML has comments / unusual formatting.** UI edits must preserve comments and field order where reasonable.
6. **Empty `gateways.yaml`.** Panel renders an empty state, not a crash.
7. **Two tabs in the registry at MVP launch.** Demonstrates the generic extension point works for the second tab from day one (no special-cased gateways logic in the tab host).
